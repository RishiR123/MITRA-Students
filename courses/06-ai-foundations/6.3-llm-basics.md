## Lesson 6.3 — LLM basics

A large language model is a neural network — the thing you built in lesson 6.2 — trained
on one absurdly simple task:

> **Given some text, predict the next token.**

That's it. Everything else — answering questions, writing code, holding a conversation —
is that one capability, scaled up and pointed at a chat interface.

---

### Tokens

Models don't see letters or words. They see **tokens**: chunks of text, usually 3–4
characters, from a fixed vocabulary of roughly 50k–200k entries.

```
"The student submitted a pull request"
  ↓
["The", " student", " submitted", " a", " pull", " request"]
  ↓
[791, 5575, 14976, 264, 6503, 1715]
```

Each token becomes an integer, and each integer indexes into a learned vector — an
**embedding**, typically a few thousand numbers long. That vector is the model's internal
representation of meaning, and similar words end up with similar vectors because that's
what makes next-token prediction easier.

Practical consequences of tokenisation, all of which will bite you eventually:

- **Rare words cost more tokens.** Common English is efficient; code, other scripts, and
  unusual names are not.
- **Models are bad at character-level tasks.** Counting the r's in "strawberry" is hard
  because the model never saw letters — it saw two or three chunks.
- **You're billed per token**, roughly ¾ of a word for English.

### Next-token prediction

The model outputs a probability for **every token in the vocabulary**:

```
"The capital of France is" →   " Paris"   0.89
                               " the"     0.04
                               " located" 0.02
                               " a"       0.01
                               ...        (~100k more)
```

Pick one, append it to the input, run again. That loop — one token at a time, each one
conditioned on everything before it — is all "generation" means.

This is also why a model streams its answer word by word. It genuinely doesn't know how
the sentence ends when it starts.

**Temperature** controls how the pick is made:

- `0` — always take the highest-probability token. Deterministic, repetitive. Use it for
  extraction, classification, structured output.
- `~1` — sample proportionally to the probabilities. More varied, more creative, more
  likely to go off the rails.

### Attention

The breakthrough that made this work, from *Attention Is All You Need* (2017).

When processing each token, the model computes how much every other token in the context
should influence it. In:

> "The student opened a pull request because **they** wanted feedback"

to predict what follows "they", the model needs "student". Attention lets it look
directly at that token — no matter how far back it is — and weight it heavily.

Mechanically, each token produces three vectors:

- **Query** — what am I looking for?
- **Key** — what do I offer?
- **Value** — what do I actually contribute?

Every query is compared against every key (a dot product — lesson 6.4), the scores are
softmaxed into weights, and the values are blended accordingly.

```
attention(Q, K, V) = softmax(QKᵀ / √dₖ) · V
```

Two things follow from this that explain most LLM behaviour:

1. **Every token can see every other token**, directly. No information has to squeeze
   through a bottleneck, which is exactly where older architectures failed on long text.
2. **Cost grows with the square of context length.** Comparing every token to every other
   token means 10× the context is ~100× the attention compute. That's why context limits
   exist and why long prompts cost real money.

### The transformer

Stack that into a block, then stack the blocks:

```
tokens → embeddings → [ attention → feed-forward ] × N → next-token probabilities
                        ↑___________________________|
                             repeat 32, 80, 100+ times
```

Each block has multi-head attention (several attentions in parallel, each learning a
different kind of relationship) followed by a small feed-forward network — the exact
`Linear → ReLU → Linear` from lesson 6.2. Add residual connections and layer
normalisation so gradients survive the depth.

**That's the whole architecture.** Its power comes from scale — parameters, data,
compute — not from conceptual complexity.

### How a chatbot gets made

1. **Pretraining** — predict the next token across a huge corpus of text. Months, enormous
   compute. Produces a model that knows language and facts but will happily continue your
   question with three more questions.
2. **Fine-tuning / instruction tuning** — train on examples of instructions and good
   responses. Now it answers instead of continuing.
3. **RLHF / preference training** — humans compare pairs of responses; the model is
   trained towards the preferred ones. This is where helpfulness, tone and refusals come
   from.

### What this explains about LLM behaviour

- **Hallucination.** The model produces plausible next tokens. Plausible and true are
  different properties, and nothing in the training objective distinguishes them. A
  confidently wrong citation is the system working exactly as designed.
- **No memory between chats.** Each request is stateless. "Memory" is your application
  resending previous messages as context.
- **Knowledge cutoff.** It knows what was in its training data. For anything current, you
  supply the information in the prompt — that's all RAG is.
- **Prompt sensitivity.** Different words shift the probability distribution. This is
  why prompt engineering works and why it feels unscientific.

### Using one

```python
import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

message = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=1024,
    messages=[
        {"role": "user", "content": "Explain gradient descent to a 12-year-old."}
    ],
)

print(message.content[0].text)
```

> **Never put your API key in the code.** Use an environment variable. The submission
> validator will fail your pull request if it finds a key, and a key pushed to GitHub is
> scraped within minutes — this is not a hypothetical.
