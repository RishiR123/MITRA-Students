## Lesson 1.1 — Why version control exists

Before you learn the commands, understand the problem they solve.

### The problem

Everyone who has written anything has invented a worse version of git:

```
essay.doc
essay_v2.doc
essay_final.doc
essay_final_REAL.doc
essay_final_REAL_use_this_one.doc
```

This breaks down immediately. You can't tell what changed between versions. You can't
merge two people's edits. You can't go back to "the version from Tuesday that worked".
And you definitely can't do any of it across five people at once.

### What git actually does

Git records **snapshots** of your project, called commits. Each commit stores:

- what every file looked like at that moment
- who made it and when
- a message saying why
- a pointer to the commit before it

That chain of commits is your project's history — complete, and permanent.

Three things follow, and they're the reason git won:

1. **You can go back.** Any commit, any time. This makes experimenting safe, which changes
   how you work.
2. **You can work in parallel.** Branches let you build a feature without touching the
   working version.
3. **You can combine work.** Git merges other people's changes into yours, and tells you
   when it can't decide.

### The mental model that makes it click

Most people struggle with git because they picture it as "a folder in the cloud". It
isn't. Picture it as three boxes on your own machine:

```
  working directory   →   staging area   →   repository
  (files you edit)        (git add)          (git commit)
```

- **Working directory** — your actual files, as you edit them.
- **Staging area** — changes you've selected for the next commit. This is the box people
  skip, and it's the one that makes git flexible: you choose *what* goes into a commit,
  not just *when*.
- **Repository** — the permanent chain of commits.

`git push` then sends commits to a fourth place, GitHub, so other people can see them.

### Git vs GitHub

They're not the same thing, and the distinction matters:

- **Git** is the version control tool. It runs on your computer. It works with no internet
  and no account.
- **GitHub** is a website that hosts git repositories and adds collaboration on top —
  pull requests, issues, reviews, CI.

You could use git your whole life without GitHub. You'll use GitHub constantly because
that's where the collaboration happens — including in this program, where every submission
you make is a pull request.

### Why this is the first module

Everything you submit here goes through git. More importantly, every software job you'll
ever have runs on this exact loop:

```
branch → commit → push → pull request → review → merge
```

Learn it properly now, once, and it stops being something you fight.

### Practice

1. Find a folder on your computer with `_final_v2`-style filenames. That's the problem
   git solves — sit with how bad it is for a moment.
2. Run `git --version`. If it isn't installed, install it now — the next lesson assumes it.
3. Explain the difference between git and GitHub to someone, out loud, without looking.

### Check yourself

- What are the three boxes a change moves through before it's committed?
- What does a commit store beyond the file contents?
- Why is the staging area useful, rather than just extra typing?
